# Storage Readiness — Proving ECS Tasks Can Be Destroyed and Replaced Without Losing Data

**Date:** 2026-07-13
**Branch:** `feature/ecs-readiness-foundation`

## Headline finding

A full-repository grep for every local-filesystem write pattern (`storage_path(`, `public_path(`, `file_put_contents(`, `fopen(`, `Storage::disk(`, `Storage::put(`, `->store(`, `->storeAs(`) found **zero real business-data writes anywhere in `app/`**. See [ec2-dependency-audit.md](ec2-dependency-audit.md) §6 for the full evidence. Every document/export/backup/scan-adjacent service is explicitly simulated by design — their own docblocks say so (`DocumentGenerationService`: "no real PDF/DOCX binary is produced"; `ExportPackageService`: "No real ZIP file is ever written to disk"; `FakeBackupRestoreDrillRunner`: "no real infrastructure I/O"; `FakeVirusScanner`: "no daemon, no network or filesystem I/O").

**This means the proof this phase asks for is already true, trivially: there is no business data on local disk to lose, because no code writes any yet.** This document records that finding precisely, classifies what local disk *is* used for today, and defines the S3 target state for when real document I/O is eventually built — without building that feature here, which is outside this mission's boundary (containerization/infra readiness, not product feature work).

## Classification of all current filesystem usage

| Category | What's there today | Where it must live |
|---|---|---|
| **Persistent business files** | **None exist yet.** No code path writes a real document, attachment, export, generated PDF, or backup file to any disk location today. | S3 (target state, prepared below) — not yet needed |
| **Generated reproducible files** | Composer/npm build artifacts (`vendor/`, `public/build/`) — regenerated by the image build, never runtime | Baked into the image at build time; irrelevant to task replacement |
| **Temporary files** | None identified beyond PHP's own `sys_temp_dir` usage (framework-internal, e.g. upload buffering before validation) | Container-local ephemeral filesystem — bounded by nature, cleaned on task replacement |
| **Caches** | `storage/framework/{cache,sessions,views}` — used only when `CACHE_STORE`/`SESSION_DRIVER` is left at the `database` default; redirected off local disk entirely once set to `redis` (staging/production target, see [queue-and-redis-architecture.md](queue-and-redis-architecture.md)) | Container-local ephemeral filesystem when used at all; Redis in staging/production |
| **Logs** | `storage/logs/laravel.log` when `LOG_CHANNEL` is left at its `single`/`stack` default | Redirected to stdout/stderr via `LOG_CHANNEL=stderr` in ECS (see [observability.md](observability.md)) — never relied upon to persist on local disk |
| **Deployment artifacts** | `bootstrap/cache/*.php` (route/config/event cache) | Baked into the image or generated at deploy time; not user data, safe to lose on task replacement |

Every row above is either build-time-baked (safe to lose — the image is the source of truth) or fully redirectable off local disk via existing env-driven config (already true for cache/session; a `LOG_CHANNEL` env change for logs). **No row requires a persistent volume, EFS mount, or any storage that must survive a task replacement.** ECS/Fargate tasks in this application can be destroyed and replaced at any time today without any data-loss risk, because there is no runtime-written business data anywhere to lose.

## Verification of specific items the mission asked to check

- **Document uploads**: `DocumentUploadPolicyService::assertUploadIsAllowed()` performs only extension/size/MIME validation (`pathinfo()`-based) — it validates a hypothetical upload's metadata, it does not receive or persist file bytes. No real upload handler exists.
- **Generated legal documents**: `DocumentGenerationService` writes a `simulated_storage_path` string column, never a real file (see audit §6).
- **Attachments**: `EmailAttachmentSafetyService`/`EmailAttachmentPromotionService` validate/route attachment *metadata*; `FakeEmailProviderClient` is fixture-driven, no real attachment bytes ever enter the system.
- **Exports**: `ExportJobService`/`ExportPackageService` maintain a status-machine of DB rows (`export_jobs`); `simulated_storage_path` again, no ZIP ever materializes.
- **Imports**: `ImportBatchService`/`ImportApplyService`/`ImportRollbackService` operate on already-parsed DB rows (`import_batches`, `import_rows`) — no evidence found of a raw file upload/parse step that would write a source file to disk (worth confirming with the owning team when import *ingestion* — as opposed to processing already-imported rows — is actually built; not present today).
- **Previews**: no preview-generation code exists (no image/PDF thumbnailing found in `app/`).
- **Backups**: `FakeBackupRestoreDrillRunner` — "no real infrastructure I/O," deterministic in-memory result only.
- **Signed download URLs**: not applicable yet — no real storage disk is written to, so there is nothing to generate a signed URL for. The `s3` disk config (`config/filesystems.php:50-61`) supports Laravel's standard `Storage::disk('s3')->temporaryUrl()` once real files exist; no code uses it today.
- **Private bucket access / encryption / content-type handling**: no bucket exists yet (no AWS SDK dependency at all — see audit §10). Target-state requirements are specified below.
- **Malware-scanning integration points**: `VirusScanner` interface + `FakeVirusScanner` implementation + `ScanDocumentJob` exist and are correctly *shaped* as an integration point (scan-then-apply-result pattern), but `ScanDocumentJob` has no dispatch call site anywhere in `app/` — it is unwired from any real upload trigger (there is no real upload trigger yet, consistent with everything else in this section).

## Target state: S3-compatible storage, prepared not built

This mission prepares the *readiness* for real document storage; it does not implement it, per the mission boundary ("do not onboard firms," containerization/infra scope only, and implementing real document I/O is a product feature change, not an infra readiness change). What's prepared:

- `config/filesystems.php`'s `s3` disk is already fully env-driven (`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`/`AWS_DEFAULT_REGION`/`AWS_BUCKET`/`AWS_URL`/`AWS_ENDPOINT`/`AWS_USE_PATH_STYLE_ENDPOINT`) — no code change needed to point it at a real bucket.
- **Preferred credential model**: an ECS task role (see [iam-matrix.md](iam-matrix.md)) with a scoped S3 bucket policy, **not** static `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` — Laravel's S3 driver (via the AWS SDK's default credential provider chain) picks up ECS task role credentials automatically when the key/secret env vars are simply left unset, so the existing config requires zero code change to work correctly either way (static keys for local dev against a real bucket if ever needed, task-role credentials in ECS).
- **Composer dependency gap** (flagged, not fixed here — a real S3 disk cannot function until this is added): `aws/aws-sdk-php` and `league/flysystem-aws-s3-v3` are not in `composer.json`'s `require` block today (only present transitively in `composer.lock` — see audit §10/§6). Adding them is a one-line `composer require league/flysystem-aws-s3-v3` when real document I/O is built; not added in this branch since there is no code yet that would use it, and adding an unused dependency is exactly the kind of scope creep this mission avoids.
- **Bucket requirements for when it's built** (documented here so the eventual work has a ready target, tracked as infrastructure inputs in [infrastructure-architecture.md](infrastructure-architecture.md) and [staging-readiness-report.md](staging-readiness-report.md)):
  - Private bucket, all public access blocked at the bucket level (S3 Block Public Access, all four settings on).
  - Default encryption at rest: SSE-KMS with a customer-managed key (not SSE-S3), so key access can be scoped per environment/tenant-sensitivity tier via the KMS key policy independently of the S3 bucket policy — see [iam-matrix.md](iam-matrix.md) for the KMS grant shape.
  - Versioning enabled (protects against accidental overwrite/delete, which matters more than usual for a legal-document platform).
  - Object-level access exclusively via time-limited signed URLs (`temporaryUrl()`) or through the application (never a public bucket URL) — content-type/malware-scan gating happens *before* a signed URL is issued, consistent with the existing `VirusScanner`/`ScanDocumentJob` shape once it's wired to a real trigger.
  - Lifecycle policy for the eventual export/backup use case (e.g., transition to Glacier after N days) is a product/retention decision for the owning team (see `RetentionPolicyService`), not something this infra branch should decide unilaterally.
  - Bucket naming/tagging should follow whatever convention [infrastructure-architecture.md](infrastructure-architecture.md)'s Terraform module inputs establish for staging vs. production separation — **no bucket is created by this branch** (Terraform is prepared but not applied, per mission constraints).

## Conclusion

No migration of existing files is needed or performed — there is nothing to migrate. ECS tasks for this application are already stateless with respect to business data. The one action item for the future (adding the S3 SDK dependency once real document I/O exists) is explicitly deferred and tracked, not implemented speculatively.
